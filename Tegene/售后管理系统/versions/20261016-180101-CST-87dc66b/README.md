# 售后打卡系统

网页、移动端和 API 文档统一使用“售后打卡系统”作为显示名称；仓库名、网址及历史源码路径保持原值。品牌图标和企业微信工作台交接见 [品牌与企微工作台交接](docs/品牌与企微工作台交接.md)。

源码位置：`Jaydon-Lidong/aftersales-field-management` 仓库根目录，以及 `shangzeng20020703/Shang/Tegene/售后管理系统`。当前售后功能及后续修改均在本项目维护，原 EHR 仅作为源码来源，不向 EHR 仓库提交或部署改动。

现场陪产可选择「现场轮休」：个人连续六上休一日历、按当天主项目规则自由打卡、待休余额流水。项目组长初次发布排班；发布后的调整按项目组长、区域组长、售后经理依次审批；攒休和调休由售后经理审批。员工可在手机端查看并申请调整。旧版使用与升级说明见 [现场轮休文档](docs/10-现场轮休.md)，其中与下方权限和审批表不一致的旧规则以本 README 为准。

基于 EHR 固定提交 `051b38f04b0e33f1e624da35fa57ecae9fd4974f` 提取的独立基础版，包含后端、电脑管理端、手机网页端和本地演示环境。

主流程为“项目库 → 售后经理分配主责区域组长（协管可留空）→ 在项目配置中先分配项目组长和组员 → 新建并关联现场轮休规则 → 打开本项目个人排班 → 按北京时间周一至周日预览和发布 → 组员按当天主项目规则打卡 → 考勤总览”。区域责任分配无需填写原因；规则建立前可保存待配置人员名单，员工能看到项目但不能按该项目打卡。“最近核验在场”、定时/随机复核和连续在场判断按要求后置。

**UI/UX 沿用原 EHR。** 手机首页、工作台、底栏、个人中心和管理端框架已恢复原版；打卡、考勤规则、审批及模板继续使用原组件，详见 [界面沿用核对](docs/08-原版UIUX沿用与核对.md)。

## 功能

### 售后现场角色与权限（2026-10-16 确认）

现场业务职级为**组员、项目组长、区域组长、售后经理**，不再另设一套“职能”维度。系统管理员和 HR 保留独立身份；旧全局 `manager` 不等于售后经理，也不自动获得现场审批或跨项目管理权。管理员任命售后经理。每项目同时只有一位项目组长，由有权管理该项目的区域组长或售后经理指定。售后经理为每项目指定一位主责区域组长和可选的协管区域组长。

| 操作 | 组员 | 项目组长 | 区域组长 | 售后经理 |
|---|---|---|---|---|
| 查看项目 | 本人参与项目 | 被任命项目 | **全部项目及人员、考勤明细** | 全部项目 |
| 管理人员与排班 | 无 | 所负责项目组员及本人 | 主责、协管项目 | 全部项目 |
| 新建、修改项目打卡规则 | 无 | 无 | 主责、协管项目 | 全部项目 |
| 分配项目组长、组员 | 无 | 无 | 主责、协管项目 | 全部项目 |
| 分配区域组长主责、协管项目 | 无 | 无 | 无 | 可以 |
| 审批请假、出差、攒休、调休 | 无 | 无 | 无 | 全部售后人员 |
| 本人打卡 | 需要 | 需要 | 不需要 | 不需要 |

组员与项目组长可从手机端发起请假、出差、调休等本人申请。HR 可查看原有管理资料，但不进入这四类售后申请的日常审批链。售后经理本人申请或经理缺席时，由系统管理员填写代审原因后处理；申请人不得审批本人。区域组长可查看所有项目，但未获分配项目只能查看，不能配置人员、排班或规则。管理端、手机端与服务端均按这一权限表校验，直接调用接口也不能绕过。

被任命的项目组长也可用本人账号进入管理端，仅显示「项目库」和「现场轮休」，并只能管理所负责项目的排班。登录及刷新时服务端复核项目组长任命；未获任命的普通组员不能进入管理端。

项目配置页按人员类别展示候选：项目组长选择框仅显示花名册中标为「项目组长候选」的在职售后员工，组员选择框仅显示标为「组员」的在职售后员工，主责和协管选择框仅显示具有区域组长系统角色的人员。花名册的「现场职能」用于维护组员与项目组长候选类别；候选标记本身不授予管理端或项目排班权限，只有获得具体项目任命后才生效。项目组长任命后自动加入项目待配置人员名单，规则启用后与组员一起出现在个人排班候选中。已有项目负责人在编辑时仍显示为当前选中值，避免因历史花名册标记缺失而无法查看配置。

### 跨项目日期与排班审批

- 一名员工**每天只有一个主项目**；10 月 16–18 日在项目 1、10 月 19–29 日在项目 2 可以连续排班。项目 1 结束后到项目 2 的交接按未来生效日期申请。两项目须先指定主责区域组长；跨区域项目调动由接收项目主责和原项目主责分别确认后生效，申请时固定两位审核人，不能由同一人完成两方审核。同一主责管理的两项目仍可调动。历史项目归属、原定轮休日和规则快照保留。
- 当天按主项目的打卡规则核对实际工时、地点和照片。白班、夜班是可选的排班展示标签，不参与工时计算。个人六上休一周期与待休余额跟随员工跨项目延续，临时休息或使用调休不重置周期。未发布的日期显示待确认；既有考勤不因后续调整静默重算。
- 项目组长可为本项目组员和本人发布初次排班，但必须遵守区域组长配置的项目规则。个人排班以北京时间周一至周日为一周，默认选中项目已分配的组员与组长、原因“周期排班”；先按个人连续六上休一周期生成建议，再逐人逐日修改，负责人确认后按周发布。已发布安排在手机端日历显示，并向每位排班人员发送站内消息；可切换查看以往各周。**发布后的任何排班变更**，包括负责人调整和员工申请，依次由项目组长、区域组长、售后经理审批，最后通过才生效；项目组长修改本人排班时跳过自己的审核节点。涉及多个项目时，各相关项目的组长和区域组长先完成审核，再交售后经理；任一节点驳回则整单不生效。申请人或代提交人若是项目唯一可审核的区域组长，售后经理须先指定另一位协管区域组长；系统不会跳过区域审核。审批期间更换职级或项目负责人不会自动把已提交申请改签给新人，卡住的申请须核对后重新提交。
- 原定轮休日出勤的攒休、额外调休使用直接由售后经理审批；待休来源、使用与撤销保留流水，不重复入账。普通轮休不扣余额。请假、出差跨项目时按日期记录对应项目及考勤影响，但整单由售后经理一次审批，驳回则整单不生效；不再拆给区域组长分别审批。
- 区域组长可在主责、协管项目新建或修改打卡规则，售后经理可对全部项目操作；修改某项目的共用规则时，先为该项目创建专用规则版本，不能连带改变其他项目。全局共用模板仍由管理员和 HR 维护；历史打卡保留原规则快照。

本次决定取代旧说明中的“区域组长只能看分配项目”“区域组长审批请假、出差、攒休、调休”“跨项目请假、出差分别按项目审批”“项目调动即时切换”及“项目负责人可直接修改已发布排班”。旧全局 `manager` 的管理权限也不能代替以上现场职级。

数据库结构现为版本 12，在版本 11 的区域责任、未来交接和请假/出差逐日项目快照基础上，新增项目待配置人员表；升级仍使用 `python -m app.bootstrap`，不会清空旧业务数据。相关接口为 `PUT /api/v1/field/projects/{project_id}/regional-leads`、`POST /api/v1/field/assignments/{id}/transfer-requests`、`GET /api/v1/field/transfer-requests`、`POST /api/v1/field/transfer-requests/{id}/review`、`POST /api/v1/field/projects/{project_id}/members/activate`、`GET/POST/PUT /api/v1/attendance/projects/{project_id}/rule` 和 `/api/v1/rotation` 下的排班、调整申请及审核接口。接口权限由服务端验证，不能只依靠页面按钮是否显示。

### 考勤看板

「考勤总览」提供人员规模、打卡进度环形图、异常类型柱状图、项目人员对比和近 7 天柱状图；支持日期、项目筛选及明细搜索、异常筛选、分页和 CSV 导出。数据来自本系统花名册、项目参与区间和考勤结果，接口为 `GET /api/v1/field/dashboard`。

- 当前在职人数：花名册中在职 / 试用人员，包含停用但未离职账号；不随日期回溯。选择项目时仅统计当前参与该项目的在职人员；区域组长可查看全部项目，项目组长仅查看被任命项目。
- 当日项目人数：所选日期参与项目的人员去重；同一天 A → B → A 只算一人。历史离职人员仍保留在当日记录中。此数是参与人数，不是按工作日历计算的应出勤人数。
- 打卡进度：任一项目有上班或下班卡即计入已打卡；当天所有项目记录均有上下班卡才计为已齐卡，其余为打卡未齐或未打卡。已齐卡不等于无异常。
- 异常人数：按人员去重；类型包含迟到、早退、缺卡、定位 / WiFi、待核对、旷工和其他异常，一人可有多类。只读取已生成的异常，不把未打卡直接认定为旷工，也不在查看看板时重算历史。
- 项目对比：各项目内部去重，展示参与人数最多的 6 个项目；跨项目人员会在各项目出现，因此项目人数之和可能大于总人数。近 7 天以所选日期为末日，按北京时间工作日统计。

`scripts/test_field_dashboard.py` 使用隔离数据库验证去重、项目筛选、权限、离职历史、空数据及跨项目规则分段统计。

### 规则配置与使用

1. 在「项目库 → 配置项目」先选择项目组长和组员。规则尚未建立时名单为“待配置”，员工可在“我的项目”看到项目，暂不能按此项目打卡；项目组长自动列入名单。
2. 区域组长在主责、协管项目内，或售后经理在全部项目内，新建现场轮休规则，设置工时、定位 / WiFi 和照片要求。关联规则后整份待配置名单须通过日期及项目冲突校验，任一人冲突则列出原因并整份保持待配置，不会部分启用；处理冲突后可重试。修改共用规则须生成项目专用版本。
3. 从项目配置点击「打开本项目个人排班」，默认选中已分配组员和组长。按北京时区周一至周日预览六上休一建议，逐人逐日调整，原因默认“周期排班”；负责人确认发布后发送站内消息，手机端个人日历显示安排。未发布的日期为“待确认”，实际打卡仍可留存；规则和首次排班尚未生效前不可按待配置项目打卡。
4. 需要打卡的组员、项目组长从员工端进入打卡，系统按当天主项目自动匹配项目规则。后续调动和已发布排班调整按上节审批路径执行。

新排班按员工每天唯一主项目校验；未来日期的项目交接由双方确认后生效，手机无须重新登录。提交打卡时服务端复核项目和规则版本。新打卡保存项目、规则快照、原始流水 ID 和计算结果。历史上同一天 A → B → A 的分段数据继续可读，缺少下班卡的旧段标记待核对，不自动补卡或跨项目配对；新写入不再允许同一天多个主项目。规则修改只影响新打卡，已打卡分段保留原规则。

项目抽屉支持 Excel / CSV 导入已有花名册人员，导入前预览核对；遇到非在职、姓名手机号不匹配、重复或已有项目的人员时整批不写入。花名册重复导入保留原密码和角色。人员状态改为离职会关闭当前和未来参与区间；恢复在职后须显式启用并重新分配项目。

数据库版本 4 曾新增参与区间和考勤分段表；原按日期安排的记录会幂等补充区间，不删除历史班次和考勤。现行按日期唯一主项目及未来交接规则见上节；旧版即时调动行为仅用于解释历史数据。执行 `python -m app.bootstrap` 后再启动，隔离测试见 `scripts/test_project_membership.py`。

数据库版本 5 新增售后名册补充资料表。下载的 Excel 保持《售后名册》的 18 列原名和原顺序，末尾追加公司在职状态，仅包含表头和一行虚构示例。人员页面使用紧凑分页列表，全部资料在编辑侧栏分组维护。手工填写姓名和联系电话后保存，自动开通手机号账号，默认密码 585858。系统已安排人员的当前项目取实时参与记录；名册中的项目、组长和部门文字不自动建立项目安排、主管权限或组织关联。是否进入企微、年龄、入职天数按登记值维护。

数据库版本 6 将旧的待入职、停用标签归为在职，保留原账号启停状态；试用期统一存储为试用。名册只接受在职、试用期、离职三种状态，在编辑中修改，列表仅展示。离职自动锁定登录、结束当前项目参与并保留历史考勤及审批数据。

后台已移除假期管理和公司管理页面、菜单及路由，已有请假审批与历史数据保留。组员主要使用员工端；项目组长、区域组长和售后经理按职责进入管理端。后台登录及每次页面导航均由服务端复核角色权限，手机端登录状态不能直接进入后台。

管理员可在「考勤管理 → 考勤规则 → 节假日表」的弹窗中维护年度节假日表，HR 可查看。2026 年初始表采用公司提供的 11 个日期；未列日期按普通工作日或周末判断，不使用国务院放假和补班预设。星期由日期自动计算，只有管理员能增删日期或修改节日名称。修改过去日期不会自动重算已生成的考勤、审批与月度汇总；正式发布前需核对既有地点特殊日与全局日历记录。

| 审批 | 请假、出差、攒休、调休由售后经理统一审批，管理员说明原因后可代审；发布后排班变更走组长→区域→经理，通用审批引擎的其他类型保留原能力 |
| 模板 | 表单控件、规则、流程设计器、版本快照、复制/导入导出、预览、发布、个人草稿持久化 |
| 通知与运维 | 站内通知、操作日志、业务事件监控、重试、考勤重算队列 |

六类初始模板：请假、加班、临时外出、补卡、出差、陪产日报。项目人员由有权管理项目的区域组长或售后经理分配，跨区域未来调动需原项目方和接收方确认；不再经过旧的派驻、现场调换、撤场三套重复申请。已有申请记录保留。

初版 231 项是供取舍的候选池，不代表本轮所有选装能力均已实现。详细实现边界和验证证据见 [交付与验收记录](docs/06-基础版交付与验收.md)。

## 接入 Tegene 项目库

**2026-09-30 已接通正式项目。** 本地管理端实际读取 `i.tegene.com` 的 89 个项目，数量与正式库核对一致。使用独立机器应用 `Aftersales Project Reader`，凭据仅保存在 `backend/.env`；人员、售后负责人和排班仍保存在本系统。

接入复用 Tegene 现有项目接口和只读集成角色 `pms-device-integration`。Logto 为售后应用单独签发 token，现有机器 token 映射中仅增加此应用的项目读取分支；其他应用映射保持原样。未修改 Tegene 业务代码、项目资料或业务数据库，也没有重启正式服务。实际 `/api/me/permissions` 仅返回 `pms:project:read`；无效凭据返回 401，访问 Logto 管理 API 返回 403。

使用路径：管理员任命售后经理；售后经理在“项目库”给项目分配主责和协管区域组长；有权管理该项目的区域组长或售后经理先指定唯一项目组长并安排组员，再新建现场轮休规则，最后按周发布个人排班。手机端“我的项目”可先查看待配置状态，规则及首周排班生效后再进入打卡页；系统自动带出当天主项目和规则。

### 精简后的业务逻辑

1. **项目库**：Tegene 是项目编号和名称的来源，售后系统不重复维护客户、现场或另一份项目列表。
2. **项目配置**：每个项目同时只有一个项目组长、一套当前打卡规则；售后经理指定区域主责和协管，有权管理项目的区域组长或售后经理先保存组长、组员名单，再新建并关联现场轮休规则。名单全部校验通过后启用，随后打开个人排班按周发布。共用规则变更先复制为项目专用版本。
3. **人员参与**：人员必须有起止日期，所选日期每天仅有一个主项目。跨区域交接用未来生效申请，由原项目方与接收方确认；批量安排中任一人失败，整批不保存。个人轮休周期和待休余额不随项目转换重置。
4. **员工打卡**：按照人员和日期匹配项目班次，自动读取打卡时段、定位/Wi-Fi/照片等规则，员工不选择项目、现场或规则。尚未分配项目时显示当前个人考勤规则，不冒充项目考勤。
   自由工时规则选择具体小时数时，双卡齐全但实际工时不足会在考勤记录和报表中标为异常，并注明差额原因；选择“不限制”不做最低工时校验。
5. **考勤查看**：“考勤总览”按项目查看应到、打卡与异常；区域组长可查看全部项目人员与考勤明细，但仅修改获分配项目。更换项目规则只影响未来未记录的打卡，已产生考勤或锁定月份的历史不改写。

不再提供独立的客户、现场、派驻列表。旧数据关联与历史记录保留，避免破坏已有考勤。本轮未改动既有正式项目的负责人或参与人员。

来源确定为 `https://i.tegene.com/api`，调用现有 `GET /pms/projects`，仅读取当前凭据有权查看的项目。读取全部项目需要上游授权全项目数据范围；不会绕过上游权限。售后经理可配置全部已接入项目；区域组长可查看全部项目，但仅管理其主责或协管项目。

在 `backend/.env` 配置（不得放到前端或提交密钥）：

```dotenv
TEGENE_API_BASE_URL=https://i.tegene.com/api
TEGENE_TOKEN_URL=https://iam.tgjqr.com/oidc/token
TEGENE_CLIENT_ID=<专用服务账号 ID>
TEGENE_CLIENT_SECRET=<专用服务账号密钥>
TEGENE_RESOURCE=https://api.robot-erp.local
TEGENE_SCOPE=pms:project:read
```

上游账号需要 `pms:project:read` 权限及覆盖全部目标项目的数据范围。短期联调也可只配置 `TEGENE_ACCESS_TOKEN`，到期后须更新；长期接入使用服务账号。配置后重启本地服务。

接入关联使用“来源地址 + Tegene UUID”，不靠名称或同号自动合并。编号和名称由 Tegene 维护；刷新项目库展示最新资料，有权管理者保存配置时同步本地关联资料。区域责任、项目组长和考勤规则由本系统配置，历史班次保留。项目重名或同号冲突会提示核对。源接口不可用时显示错误，已接入项目和本地历史排班仍可使用。

结构升级只追加关联表，运行 `PYTHONPATH=backend backend/.venv/bin/python -m app.bootstrap` 后重启。验证命令：`backend/.venv/bin/python scripts/test_tegene_projects.py`，使用临时数据库和模拟上游，不触碰正式项目。本次实现按仓库主干 `7ec6e0bd1785d4a7f754fd7e4c0b02f5700ca5cf` 的 API 契约验证；未配置真实凭据前不代表正式数据已接通。

## 配置定位服务

复制 `backend/.env.example` 为 `backend/.env`，配置后重启后端：

- `TENCENT_MAP_WEB_SERVICE_KEY`：后端坐标转换、逆地址解析和地图代理。
- `TENCENT_MAP_BROWSER_KEY`：浏览器地图展示 Key 的服务器回退值。管理员专用后端接口 `GET/PUT/DELETE /api/v1/system-settings/tencent-map` 可管理数据库覆盖值；后台保存值优先，清除后回退到此环境变量。修改数据库覆盖值后刷新已打开的手机端地图页即可生效。管理端不提供配置页面。浏览器 Key 应在腾讯控制台限制实际使用域名；服务端 Key 不下发给浏览器。

演示规则不要求 GPS，便于先体验流程。正式现场需在考勤规则中配置真实坐标、范围和照片要求。GPS 规则采用腾讯地图坐标口径；IP 地址定位只作地址提示，不作为打卡坐标。
