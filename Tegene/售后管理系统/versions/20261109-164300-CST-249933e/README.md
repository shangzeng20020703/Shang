# 售后打卡系统

网页、移动端和 API 文档统一使用“售后打卡系统”作为显示名称；仓库名、网址及历史源码路径保持原值。品牌图标和企业微信工作台交接见 [品牌与企微工作台交接](docs/品牌与企微工作台交接.md)。

源码位置：`Jaydon-Lidong/aftersales-field-management` 仓库根目录，以及 `shangzeng20020703/Shang/Tegene/售后管理系统`。当前售后功能及后续修改均在本项目维护，原 EHR 仅作为源码来源，不向 EHR 仓库提交或部署改动。

现场陪产可选择「现场轮休」：负责人逐人确认上 6 休 1、上 12 休 2、上 18 休 3 或自定义排班；员工按当天主项目规则自由打卡，每累计 6 个有效工作日获得 1 天休息额度，未满 6 天的进度跨现场轮休项目保留。规则建立前的个人计划只供查看，规则保存后才正式生效；后续调整按项目组长、区域组长、售后经理依次审批。员工可在手机端查看本人可用额度、累计进度和流水并申请集中休息。使用与升级说明见 [现场轮休文档](docs/10-现场轮休.md)。

基于 EHR 固定提交 `051b38f04b0e33f1e624da35fa57ecae9fd4974f` 提取的独立基础版，包含后端、电脑管理端、手机网页端和本地演示环境。

主流程为“项目库 → 售后经理分配主责区域组长（协管可留空）→ 在项目配置中选项目组长及组员并一次确认人员配置 → 为组长和全部组员确认个人排班 → 新建并保存本项目现场轮休规则 → 已确认排班绑定规则后生效 → 组员按当天主项目规则打卡 → 考勤总览”。区域责任分配无需填写原因；规则建立前已确认的名单和排班只处于待生效状态，员工能看到项目和计划，但不能按该项目打卡或据此累计待休。“最近核验在场”、定时/随机复核和连续在场判断按要求后置。

**UI/UX 沿用原 EHR。** 手机首页、工作台、底栏、个人中心和管理端框架已恢复原版；打卡、考勤规则、审批及模板继续使用原组件，详见 [界面沿用核对](docs/08-原版UIUX沿用与核对.md)。

## 功能

### 售后现场角色与权限（2026-10-16 确认）

现场业务职级为**组员、项目组长、区域组长、售后经理**，不再另设一套“职能”维度。系统管理员和 HR 保留独立身份；旧全局 `manager` 不等于售后经理，也不自动获得现场审批或跨项目管理权。管理员任命售后经理。每项目同时只有一位项目组长，由有权管理该项目的区域组长或售后经理指定。售后经理为每项目指定一位主责区域组长和可选的协管区域组长。

| 操作 | 组员 | 项目组长 | 区域组长 | 售后经理 |
|---|---|---|---|---|
| 查看项目 | 本人参与项目 | 被任命项目 | **全部项目及人员、考勤明细** | 全部项目 |
| 管理人员与排班 | 无 | 所负责项目组员及本人 | 主责、协管项目 | 全部项目 |
| 新建、修改项目打卡规则 | 无 | 无 | 主责、协管项目 | 全部项目 |
| 分配项目组长、组员 | 无 | 无 | 主责、协管项目 | 全部项目 |
| 分配区域组长主责、协管项目 | 无 | 无 | 无 | 可以 |
| 审批请假、出差、攒休、调休 | 无 | 无 | 无 | 全部售后人员 |
| 本人打卡 | 需要 | 需要 | 不需要 | 不需要 |

组员与项目组长可从手机端发起请假、出差、调休等本人申请。HR 可查看原有管理资料，但不进入这四类售后申请的日常审批链。售后经理本人申请或经理缺席时，由系统管理员填写代审原因后处理；申请人不得审批本人。区域组长可查看所有项目，但未获分配项目只能查看，不能配置人员、排班或规则。管理端、手机端与服务端均按这一权限表校验，直接调用接口也不能绕过。

被任命的项目组长也可用本人账号进入管理端，首页和侧边栏只显示「项目库」，从所负责项目的「打开本项目个人排班」进入排班页；只能管理所负责项目的排班。登录及刷新时服务端复核项目组长任命；未获任命的普通组员不能进入管理端。其他管理角色也从项目配置中的个人排班按钮进入排班页；「现场轮休」不再单列在侧边栏。

项目配置页按人员类别展示候选：项目组长选择框仅显示花名册中标为「项目组长候选」的在职售后员工，组员选择框仅显示标为「组员」的在职售后员工，主责和协管选择框仅显示具有区域组长系统角色的人员。花名册的「现场职能」用于维护组员与项目组长候选类别；候选标记本身不授予管理端或项目排班权限，只有获得具体项目任命后才生效。未建立规则的项目先选择一名组长和至少一名组员，点击一次「确认人员配置」原子保存整份待配置名单；再次确认以当前所选组员替换先前待配置组员，组长自动加入。确认名单后分别设置每个人的起点、模板和日期，可逐人保存完整周期；这时排班只作为待规则生效计划，不开放打卡或待休计算。已确认计划中的人员不能直接从待配置名单移除，需先处理其计划。已有项目负责人在编辑时仍显示为当前选中值，避免因历史花名册标记缺失而无法查看配置。

### 跨项目日期与排班审批

- 一名员工**每天只有一个主项目**；10 月 16–18 日在项目 1、10 月 19–29 日在项目 2 可以连续排班。项目 1 结束后到项目 2 的交接按未来生效日期申请。两项目须先指定主责区域组长；跨区域项目调动由接收项目主责和原项目主责分别确认后生效，申请时固定两位审核人，不能由同一人完成两方审核。同一主责管理的两项目仍可调动。历史项目归属、原定轮休日和规则快照保留。
- 当天按主项目的打卡规则核对实际工时、地点和照片。白班、夜班是可选的排班展示标签，不参与工时计算。个人排班及有效工作日累计进度跟随员工跨现场轮休项目延续，临时休息或使用额度不清零进度；未来项目未知的日期可先标为「待分配项目」，不能据此打卡。未发布的日期显示待确认；既有考勤不因后续调整静默重算。
- 项目组长可为本项目组员和本人确认初次排班，待项目规则保存后正式生效。每人独立设置开始日期及周期起点，选上 6 休 1、上 12 休 2、上 18 休 3 模板或自定义逐日调整，并按选定日期范围重复生成；原因默认“周期排班”。规则前每位名单成员须有至少一个完整周期的个人计划（自定义至少 7 天），允许后续日期暂未分配项目；项目只绑定属于自己的日期。规则保存后，已确认计划绑定项目规则并正式发布，站内消息通知相关人员，手机端日历显示安排。**正式发布后的任何排班变更**，包括负责人调整和员工申请，依次由项目组长、区域组长、售后经理审批，最后通过才生效；项目组长修改本人排班时跳过自己的审核节点。涉及多个项目时，各相关项目的组长和区域组长先完成审核，再交售后经理；任一节点驳回则整单不生效。申请人或代提交人若是项目唯一可审核的区域组长，售后经理须先指定另一位协管区域组长；系统不会跳过区域审核。审批期间更换职级或项目负责人不会自动把已提交申请改签给新人，卡住的申请须核对后重新提交。
- 每满 6 个有效工作日自动入账 1 天现场轮休额度，并保留余下进度；满当天项目要求工时计 1 天，达到一半但未满额须经售后经理确认才计 0.5 天。已批准出差在经理确认实际工作后计入，同一日期最多计 1 天。常规上 6 休 1 休息日额度足够时自动扣除；延后或集中休息由员工申请、售后经理批准后扣除。尚未攒够可先排「待兑现」休息计划，到期未满足条件标为「待处理」，不静默判正常或旷工。待休来源、使用与撤销保留流水，不重复入账。请假、出差跨项目时按日期记录对应项目及考勤影响，但整单由售后经理一次审批，驳回则整单不生效；不再拆给区域组长分别审批。
- 区域组长可在主责、协管项目新建或修改打卡规则，售后经理可对全部项目操作；修改某项目的共用规则时，先为该项目创建专用规则版本，不能连带改变其他项目。全局共用模板仍由管理员和 HR 维护；历史打卡保留原规则快照。

本次决定取代旧说明中的“区域组长只能看分配项目”“区域组长审批请假、出差、攒休、调休”“跨项目请假、出差分别按项目审批”“项目调动即时切换”及“项目负责人可直接修改已发布排班”。旧全局 `manager` 的管理权限也不能代替以上现场职级。

数据库结构现为版本 16：旧项目待配置人员及规则前排班表保留，逐人计划、计划日期、滚动休息额度记录及项目地点导入目录继续可用；项目表导入的项目允许暂缺客户和项目组长。升级仍使用 `python -m app.bootstrap`，迁移保留旧项目及关联记录，并将已有的纯导入目录项目补建为可配置项目。人员配置接口为 `PUT /api/v1/field/projects/{project_id}/pending-roster` 和 `POST /api/v1/field/tegene/projects/{external_id}/pending-roster`；每人排班使用 `/api/v1/rotation/projects/{project_id}/person-plans/{employee_id}` 的读取、预览及确认接口，未来待分配日期在项目调动确认后通过同一路径的 `/bind` 操作绑定目标项目。管理员通过 `/api/v1/rotation/entitlement/policy` 设置滚动算法生效日期；如果拟生效日期已有现场轮休打卡，必须改选之后的日期，避免旧余额与新额度重复。员工仅通过 `/api/v1/rotation/me/entitlement` 读取本人全部项目合计的额度与进度。售后经理通过 `/api/v1/rotation/entitlement/pending` 和日期确认接口处理半天及出差出勤。规则前确认只写待生效计划，不写正式考勤日或额度流水。接口权限由服务端验证，不能只依靠页面按钮是否显示。

### 考勤看板

「考勤总览」提供人员规模、打卡进度环形图、异常类型柱状图、项目人员对比和近 7 天柱状图；支持日期、项目筛选及明细搜索、异常筛选、分页和 CSV 导出。数据来自本系统花名册、项目参与区间和考勤结果，接口为 `GET /api/v1/field/dashboard`。

- 当前在职人数：花名册中在职 / 试用人员，包含停用但未离职账号；不随日期回溯。选择项目时仅统计当前参与该项目的在职人员；区域组长可查看全部项目，项目组长仅查看被任命项目。
- 当日项目人数：所选日期参与项目的人员去重；同一天 A → B → A 只算一人。历史离职人员仍保留在当日记录中。此数是参与人数，不是按工作日历计算的应出勤人数。
- 打卡进度：任一项目有上班或下班卡即计入已打卡；当天所有项目记录均有上下班卡才计为已齐卡，其余为打卡未齐或未打卡。已齐卡不等于无异常。
- 异常人数：按人员去重；类型包含迟到、早退、缺卡、定位 / WiFi、待核对、旷工和其他异常，一人可有多类。只读取已生成的异常，不把未打卡直接认定为旷工，也不在查看看板时重算历史。
- 项目对比：各项目内部去重，展示参与人数最多的 6 个项目；跨项目人员会在各项目出现，因此项目人数之和可能大于总人数。近 7 天以所选日期为末日，按北京时间工作日统计。

`scripts/test_field_dashboard.py` 使用隔离数据库验证去重、项目筛选、权限、离职历史、空数据及跨项目规则分段统计。

### 规则配置与使用

1. 在「项目库 → 配置项目」选择项目组长和组员，点击「确认人员配置」一次保存完整名单。项目组长自动列入名单。未建立规则时，员工可在“我的项目”看到待配置项目，暂不能按此项目打卡。再次确认会以当前所选组员替换旧待配置名单；若有人已有待生效计划，应先处理该计划，不会静默遗留计划。
2. 点击「打开本项目个人排班」，逐人设置开始日期、周期起点和模板（上 6 休 1、上 12 休 2、上 18 休 3 或自定义），可逐日调整并按日期范围重复生成，原因默认“周期排班”。每个人独立保存至少一个完整周期；未来项目未确定的日期可以标为「待分配」。手机端能查看待生效计划，此时不能按计划打卡、计工时或获得休息额度。人员、日期或项目冲突须先处理。
3. 每位已确认成员均完成个人计划后，区域组长可在主责、协管项目内，售后经理可在全部项目内新建并**保存**现场轮休规则，设置工时、定位 / WiFi 和照片要求。首次保存时整份名单及属于本项目的计划日期统一校验；任一人冲突则列出姓名、冲突项目和原因，不部分启用。未来待分配项目的日期保留个人周期，但没有项目规则、不能打卡。涉及其他项目仍按既有双方确认的调动流程处理。
4. 保存规则成功后，属于该项目的待生效计划绑定规则并正式发布，向相关人员发送站内消息；需要打卡的组员、项目组长从员工端进入打卡，系统按当天主项目自动匹配项目规则。已正式发布排班的调整按上节审批路径执行。修改共用规则须生成项目专用版本；历史考勤不自动重算。

新排班按员工每天唯一主项目校验；未来日期的项目交接由双方确认后生效，手机无须重新登录。提交打卡时服务端复核项目和规则版本。新打卡保存项目、规则快照、原始流水 ID 和计算结果。历史上同一天 A → B → A 的分段数据继续可读，缺少下班卡的旧段标记待核对，不自动补卡或跨项目配对；新写入不再允许同一天多个主项目。规则修改只影响新打卡，已打卡分段保留原规则。

项目抽屉支持 Excel / CSV 导入已有花名册人员，导入前预览核对；遇到非在职、姓名手机号不匹配、重复或已有项目的人员时整批不写入。花名册重复导入保留原密码和角色。人员状态改为离职会关闭当前和未来参与区间；恢复在职后须显式启用并重新分配项目。

数据库版本 4 曾新增参与区间和考勤分段表；原按日期安排的记录会幂等补充区间，不删除历史班次和考勤。现行按日期唯一主项目及未来交接规则见上节；旧版即时调动行为仅用于解释历史数据。执行 `python -m app.bootstrap` 后再启动，隔离测试见 `scripts/test_project_membership.py`。

数据库版本 5 新增售后名册补充资料表。下载的 Excel 保持《售后名册》的 18 列原名和原顺序，末尾追加公司在职状态，仅包含表头和一行虚构示例。人员页面使用紧凑分页列表，全部资料在编辑侧栏分组维护。手工填写姓名和联系电话后保存，自动开通手机号账号，默认密码 585858。系统已安排人员的当前项目取实时参与记录；名册中的项目、组长和部门文字不自动建立项目安排、主管权限或组织关联。是否进入企微、年龄、入职天数按登记值维护。

数据库版本 6 将旧的待入职、停用标签归为在职，保留原账号启停状态；试用期统一存储为试用。名册只接受在职、试用期、离职三种状态，在编辑中修改，列表仅展示。离职自动锁定登录、结束当前项目参与并保留历史考勤及审批数据。

后台已移除假期管理和公司管理页面、菜单及路由，已有请假审批与历史数据保留。组员主要使用员工端；项目组长、区域组长和售后经理按职责进入管理端。后台登录及每次页面导航均由服务端复核角色权限，手机端登录状态不能直接进入后台。

管理员可在「考勤管理 → 考勤规则 → 节假日表」的弹窗中维护年度节假日表，HR 可查看。2026 年初始表采用公司提供的 11 个日期；未列日期按普通工作日或周末判断，不使用国务院放假和补班预设。星期由日期自动计算，只有管理员能增删日期或修改节日名称。修改过去日期不会自动重算已生成的考勤、审批与月度汇总；正式发布前需核对既有地点特殊日与全局日历记录。

## 安装与启动

需要 Python 3.11+、Node.js 22+、npm；有 `uv` 时安装脚本优先使用 `uv`。

```sh
./scripts/setup.sh --admin
python3 scripts/dev.py start
python3 scripts/dev.py status
python3 scripts/dev.py stop
```

安装脚本创建本项目虚拟环境、安装依赖、非破坏性初始化本地 SQLite 空表；全新环境用 `app.bootstrap --admin` 初始化管理员与模板，只有显式运行 `./scripts/setup.sh --demo` 才创建演示数据。已有数据不会被清空，已有账号密码不会被重置。启动脚本仅管理本项目启动的进程；端口被其他进程占用时会报错。

- 本地数据库：`backend/data/aftersales.db`
- 上传文件：`backend/uploads/`
- 本地会话密钥：`backend/data/.session-key`
- 运行日志：`.runtime/`

## 接入 Tegene 项目库

**2026-09-30 已接通正式项目。** 本地管理端实际读取 `i.tegene.com` 的 89 个项目，数量与正式库核对一致。使用独立机器应用 `Aftersales Project Reader`，凭据仅保存在 `backend/.env`；人员、售后负责人和排班仍保存在本系统。

接入复用 Tegene 现有项目接口和只读集成角色 `pms-device-integration`。Logto 为售后应用单独签发 token，现有机器 token 映射中仅增加此应用的项目读取分支；其他应用映射保持原样。未修改 Tegene 业务代码、项目资料或业务数据库，也没有重启正式服务。实际 `/api/me/permissions` 仅返回 `pms:project:read`；无效凭据返回 401，访问 Logto 管理 API 返回 403。

使用路径：管理员任命售后经理；售后经理在“项目库”给项目分配主责和协管区域组长；有权管理该项目的区域组长或售后经理一次确认唯一项目组长及组员的待配置名单，由负责人逐人确认完整个人排班，再新建并保存现场轮休规则。属于该项目的人员和排班生效后方可按项目打卡。手机端“我的项目”可先查看待配置状态和待生效计划；规则生效后系统自动带出当天主项目和规则。

### 精简后的业务逻辑

1. **项目库**：Tegene 项目接口保持只读；售后系统可另外导入项目编号、名称、位置及定位要求。按项目编号合并展示，本地导入名称优先用于售后页面，未关联上游的项目先列为「待配置」。
2. **项目配置**：每个项目同时只有一个项目组长、一套当前打卡规则；售后经理指定区域主责和协管，有权管理项目的区域组长或售后经理一次确认组长及完整组员名单。负责人逐人确认至少一个完整个人周期，计划先待生效；规则保存并通过整组校验后启用属于该项目的人员与排班日期。共用规则变更先复制为项目专用版本。
3. **人员参与**：人员必须有起止日期，所选日期每天仅有一个主项目。跨区域交接用未来生效申请，由原项目方与接收方确认；批量安排中任一人失败，整批不保存。个人轮休周期和待休余额不随项目转换重置。
4. **员工打卡**：按照人员和日期匹配项目班次，自动读取打卡时段、定位/Wi-Fi/照片等规则，员工不选择项目、现场或规则。尚未分配项目时显示当前个人考勤规则，不冒充项目考勤。
   自由工时规则选择具体小时数时，双卡齐全但实际工时不足会在考勤记录和报表中标为异常，并注明差额原因；选择“不限制”不做最低工时校验。
5. **考勤查看**：“考勤总览”按项目查看应到、打卡与异常；区域组长可查看全部项目人员与考勤明细，但仅修改获分配项目。更换项目规则只影响未来未记录的打卡，已产生考勤或锁定月份的历史不改写。

不再提供独立的客户、现场、派驻列表。旧数据关联与历史记录保留，避免破坏已有考勤。本轮未改动既有正式项目的负责人或参与人员。

来源确定为 `https://i.tegene.com/api`，调用现有 `GET /pms/projects`，仅读取当前凭据有权查看的项目。读取全部项目需要上游授权全项目数据范围；不会绕过上游权限。售后经理可配置全部已接入项目；区域组长可查看全部项目，但仅管理其主责或协管项目。

在 `backend/.env` 配置（不得放到前端或提交密钥）：

```dotenv
TEGENE_API_BASE_URL=https://i.tegene.com/api
TEGENE_TOKEN_URL=https://iam.tgjqr.com/oidc/token
TEGENE_CLIENT_ID=<专用服务账号 ID>
TEGENE_CLIENT_SECRET=<专用服务账号密钥>
TEGENE_RESOURCE=https://api.robot-erp.local
TEGENE_SCOPE=pms:project:read
```

上游账号需要 `pms:project:read` 权限及覆盖全部目标项目的数据范围。短期联调也可只配置 `TEGENE_ACCESS_TOKEN`，到期后须更新；长期接入使用服务账号。配置后重启本地服务。

接入关联使用“来源地址 + Tegene UUID”，不靠名称自动合并。Tegene 的业务资料仍由其维护；售后项目地点表按项目编号与本地项目目录合并，本地导入的名称为售后页面显示名称，上游刷新不得覆盖。区域责任、项目组长和考勤规则由本系统配置，历史班次保留。项目编号冲突须在导入预览中核对；源接口不可用时，已接入项目和本地历史排班仍可使用。

结构升级只追加关联表，运行 `PYTHONPATH=backend backend/.venv/bin/python -m app.bootstrap` 后重启。验证命令：`backend/.venv/bin/python scripts/test_tegene_projects.py`，使用临时数据库和模拟上游，不触碰正式项目。本次实现按仓库主干 `7ec6e0bd1785d4a7f754fd7e4c0b02f5700ca5cf` 的 API 契约验证；未配置真实凭据前不代表正式数据已接通。

## 配置定位服务

复制 `backend/.env.example` 为 `backend/.env`，配置后重启后端：

- `TENCENT_MAP_WEB_SERVICE_KEY`：后端坐标转换、逆地址解析和地图代理。
- `TENCENT_MAP_BROWSER_KEY`：浏览器地图展示 Key 的服务器回退值。管理员专用后端接口 `GET/PUT/DELETE /api/v1/system-settings/tencent-map` 可管理数据库覆盖值；后台保存值优先，清除后回退到此环境变量。修改数据库覆盖值后刷新已打开的手机端地图页即可生效。管理端不提供配置页面。浏览器 Key 应在腾讯控制台限制实际使用域名；服务端 Key 不下发给浏览器。

演示规则不要求 GPS，便于先体验流程。正式现场需在考勤规则中配置真实坐标、范围和照片要求。GPS 规则采用腾讯地图坐标口径；IP 地址定位只作地址提示，不作为打卡坐标。

### 项目地点表导入与打卡位置

「项目库 → 导入项目与打卡位置」使用 Excel 模板，只读取「项目编号、项目名称、地理位置、是否需要定位」四列。项目编号是合并键，重复导入先预览差异，再确认写入，不产生同号副本。地理位置单元格中的腾讯地图链接提供坐标；地点文字仅用于显示，不能替代坐标。导入后项目立即进入项目库，可由售后经理分配主责、协管区域组长；无需先填写客户资料。随后由有权管理该项目的人员一次确认项目组长和组员，再逐人确认排班，最后保存现场轮休规则。未确认人员、排班和规则时项目保持待配置状态，不能按该项目打卡。客户资料可后续补录，不影响人员配置和排班。

接口为 `POST /api/v1/field/projects/import/preview` 和 `POST /api/v1/field/projects/import/commit`（上传同一文件及预览令牌；已有规则需逐项目显式确认）；`GET /api/v1/field/projects/catalog` 读取本地目录。导入时按编号建立可配置项目，保留旧版 `POST /api/v1/field/projects/catalog/{code}/promote` 作为兼容入口；新页面通过既有项目人员配置接口确认组长和组员。管理员、售后经理可在项目抽屉后补客户资料，使用 `PATCH /api/v1/field/projects/{project_id}/customer`，不改变人员、排班或规则。`GET /api/v1/attendance/projects/{project_id}/rule-defaults` 返回新规则可编辑的项目地点默认值。导入不自动建立规则、排班或人员。

「需要定位」且表格有有效坐标时，新规则预填该项目地点、腾讯地图坐标和 300 米半径，管理员可在规则中修改半径。没有有效坐标时，必须先在规则中手动设置打卡位置；服务端拒绝保存没有有效范围的定位规则，也拒绝通过缺少范围的定位打卡。选择「不需要定位」仅关闭 GPS 要求，Wi-Fi、设备和照片等其他要求仍按规则执行。员工按当天所属项目读取该项目规则及打卡位置，实际打卡地址仍记录本人定位结果。

再次导入若会影响已有生效规则，先列出差异，由有权管理者明确确认后才更新表格管理的地点；手工增设地点和历史打卡、规则快照不被覆盖。导入只开放给管理员和售后经理；区域组长可查看全部项目，仅能修改获分配项目的规则。表格原件、项目地点业务数据和独立本地预览库不提交 GitHub；正式环境必须另行核对后才能导入。
