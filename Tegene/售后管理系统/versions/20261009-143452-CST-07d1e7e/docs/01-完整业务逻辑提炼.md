# 售后管理系统——完整业务逻辑提炼

版本：V1.0（宽范围保留版）｜日期：2026-09-29｜用途：业务删减、产品设计、开发输入。

源码基线：EHR `main`，提交 `051b38f04b0e33f1e624da35fa57ecae9fd4974f`。本文以源码静态核对为依据，不表示原系统已经在生产通过验收。S01—S48 的固定提交链接见 [源码证据索引](04-源码证据索引.md)。

## 1. 提炼结论与系统定位

EHR 可以提供“人员与组织 → 考勤规则 → 手机打卡 → 异常申请 → 模板审批 → 业务回写 → 日/月统计”的大部分基础能力。售后系统应围绕“客户现场、陪产任务、派驻人员、计划班次、现场证据”重新组织这些能力。

本系统需要回答：某项目今天需要谁到场；他是否按时提供有效到场证据；最近一次核验何时发生；是否已离场、获批外出或请假；缺证据和异常由谁处理；事后能否重建判断依据。

**普通上下班打卡只能证明若干时点，无法直接证明整个班次持续在场。** 页面必须区分“计划驻场”“最近核验在场”“已离场”“获批暂离”“超时未核验”“定位待核验”等状态。审批同意、出差中、考勤正常均不能直接替代现场证据。

本次先尽量保留原有能力，采用功能开关和可删减清单，不提前删除加班、调休、请假、报表、审批高级配置等相关逻辑。完整薪资、招聘、绩效、培训、资产和聊天作为外围备选，不成为独立运行的硬依赖。

## 4. 原打卡规则的实际逻辑

### 4.1 规则匹配（已有）

来源 S01、S02。

1. 查询员工当日排班；有排班则优先使用关联规则与班次时间。
2. 无排班时，从已启用、已生效的考勤规则中匹配。
3. 先校验主字段中的部门、地点、人员类型；再执行排除人员、明确指定人员与自定义范围。
4. 自定义范围可由部门（可含下级）、人员、配置内考勤组和标签匹配；组/标签有解析路径，但不宜当作完整独立主数据系统。
5. 多规则匹配时：优先级数字小者优先 → 同优先级选更具体范围 → 生效日期较新者 → ID 较小者。
6. 具体范围分值为人员 400、组/标签/岗位类别 300、部门 200、全员 100。岗位在分值判断中出现，不意味着完整岗位适用判定已实现。
7. 规则支持复制、启停、日志和冲突检查；冲突检查不等于所有配置组合均已保证互斥。

售后改造：必须先验证有效派驻和现场授权，再选择该任务的规则版本；同一人可跨项目派驻，不能只用所属部门决定当天现场。禁止将项目 A 的定位证据用于项目 B。

### 4.2 工作日、班次与工时（已有，需校正）

来源 S02、S05、S07、S08。

- 工时制度为 `standard/flexible/comprehensive`；规则类型还有固定、自由、排班等扩展配置，两套概念不能简单合并。
- 工作日历依次查地点专属、全局、内置 2025/2026 节假日，再按星期兜底。后续年份必须可维护，不能永久依赖内置两年数据。
- 支持特殊必打卡日、免打卡日、免打卡人员、周末/节假日是否打卡、手动或匹配班次。
- 自由班可配置业务日开始时间，切点前的打卡归前一天。原固定/排班跨夜归属必须专门复核；工时计算会跨日，并不表示所有跨夜卡点已正确归班。
- 有上下班卡时，实际工时按两卡间隔扣除相交休息段，最低为 0，保留两位；缺卡则可能为 `None`。
- 固定/排班状态主要看缺卡、迟到、早退和半天旷工阈值；存在晚到晚走、早到早走等弹性偏移模式。
- 自由/弹性场景两卡齐全通常为正常，没有统一的“低于最低工时即异常”判断。
- 上下班同分钟、全天窗口误配和 0 工时可能不能被现有状态完整识别；必须独立处理。

售后改造：计划服务分钟、有效证据覆盖分钟、人工认可分钟、出勤统计分钟分别计算；休息、批准暂离、缺证据不能自动算成实际现场服务时长。

### 4.3 定位与打卡方法（已有，存在宽松边界）

来源 S03、S04、S29、S33。

| 原逻辑 | 实际行为 | 售后规则建议 |
|---|---|---|
| GPS 围栏 | Haversine 距离、多地点、半径范围 | 围栏必须绑定当前现场及版本；未配坐标应拒绝发布严格规则 |
| GPS + Wi-Fi | 默认任一通过；`all/both/and` 要求同时通过 | 由现场规则明确“任一/全部”，不能默认为强定位 |
| Wi-Fi | 主要对比提交的 SSID 名称 | 增加能力可用性说明；SSID 字符串不等于可信设备认证 |
| 拍照 | 原 `require_photo` 在方法不通过且无照片时追加异常 | 增加独立的每次必拍/仅异常拍照开关；校验真实文件对象 |
| 模拟定位 | 处理客户端上报的 `is_mock_location` | 只能作为风险信号；不能宣称已可靠识别所有虚拟定位 |
| 预检 | 返回规则、卡点、时间窗与异常；未命中规则可能返回 valid | 严格现场模式必须要求有效派驻、规则及新鲜证据 |
| 正式打卡 | 服务器取当前时间；存在异常时仍可记录流水 | “已收到记录”和“有效到场核验”分开返回 |
| H5/原生 | 浏览器与 Capacitor 定位适配，能取得精度和时间 | 将 provider、accuracy、采集时间传到后端并执行阈值判断 |
| 地图 | 腾讯坐标转换、逆地理、搜索、IP 定位等入口 | 原始坐标、转换坐标、坐标系分别保存；IP 定位不得作为到场证据 |

原移动端具有水印照片上传，也存在无文件时生成 `outside:...` 文本的兼容路径。字符串非空不能作为“现场照片存在”的依据。水印是辅助追踪信息，不能单独证明拍摄时间和真实性。

### 4.4 原始记录与日报（已有）

来源 S04、S09、S15。

- 每次打卡写原始流水；日报取最早上班、最晚下班。
- 保存位置、Wi-Fi、设备说明、照片、来源与异常文本；来源包括手机、门禁、人工及审批补卡流水。
- 设备字段/来源枚举存在，不代表已经有门禁或人脸硬件接入。
- 打卡后更新日结果并刷新未锁定月汇总。
- 展示状态可能同时拼接位置异常和迟到等信息，数据库单一 `status` 与页面复合 `display_status` 不完全等价。

售后改造：原始事件只追加；有效/无效、冲正、审批认可写独立结果或修订记录。到场和离场时间不能直接等同于连续现场时长；多次暂离需要多个区间。

### 4.5 补卡与异常申诉（已有，入口必须统一）

来源 S06、S11、S42、S44。

补卡资格服务会检查规则开关、可补异常类型、过去 N 天、次月截止日、月次数、是否已锁月、该日是否应出勤、同卡点待审批重复申请、班次时间是否合法，并返回可补日期/卡点与拒绝原因。

这些校验是重要可复用能力，但单独的资格查询接口不能替代正式提交、最终批准时的再次校验；所有动态模板入口都必须落到同一资格服务。

原申诉/旧修正通过路径可直接把记录置为正常并清空异常。售后系统应保留原异常，新增“已解释/人工认可/复核通过”状态与理由；补卡审批不能伪造当时采集过 GPS 的事实。

### 4.6 加班、请假、出差、外出（已有/可选）

来源 S05、S08、S11。

- 加班策略包含按审批、按打卡、审批与打卡结合，工作日/休息日/节假日，起算阈值、休息扣减、取整、调休与加班费拆分。
- 请假/出差/外出/补卡/加班审批可生成 `AttendanceEffect`，作用到人员、日期或时段。
- 请假及外出可以解释缺卡，出差可计入出差天数；这与售后现场在场判断不同。
- 调休余额、假种、余额单位和薪酬费率有跨模块依赖；作为可选结算适配保留，不能为一个打卡动作强制加载整套薪资。
- 在新系统中，“去客户现场出差”仅说明任务和行程获批，到场仍需现场核验；请假、外出应减少应在场义务或解释离场，而非增加在场人数。

### 4.7 日报、月报与锁定（已有）

来源 S08—S10。

- 管理端有打卡记录、原始打卡时间日历、日报/月报、排班、异常和规则入口；支持筛选、统计及 Excel 导出。
- 月汇总状态为 `draft → employee_confirmed → locked`。实际锁定服务仅锁定本人已确认记录；接口注释的宽泛描述不能作为规则依据。
- 汇总生成/刷新会保留已锁定快照；这不能证明所有打卡、申诉、审批回写入口都禁止改动锁定月的基础记录。
- 月报支持任务创建、查询、结果和导出；正在运行的任务状态在进程内，完成结果写数据库快照，并非完整分布式任务队列。

售后月报应按项目、现场、任务、人员、外协单位分组；同时保留原始证据、计算值、认可值、修订版本，锁定后通过受控调整单修改并重新确认。

## 5. 原审批平台的实际逻辑

### 5.1 模板生命周期（已有，发布边界需加固）

来源 S16、S22、S25、S44、S47。

模板包括名称、业务编码、分组、图标、排序、适用端、描述、启停、字段、打印格式、权限、异常策略和流程。已有保存、复制、启停、批量停用、导出、版本查询、发布及实例归档入口。

流程及模板快照用于保持历史实例上下文。原保存接口可默认把模板设为 enabled；提交时无版本还可能创建 published 版本，因此不能将原实现描述为严格的“只有显式发布版本才能被使用”。

新系统必须分离“编辑草稿”和“生效版本”：草稿保存不影响当前已发布版本；发布验证完整性；每次申请固定模板、表单、流程、规则及业务绑定版本；停用只禁止新申请，不破坏在途和历史。

### 5.2 表单设计（已有控件较多，部分只有基础校验）

来源 S17、S28、S31、S44。

| 控件类别 | 原控件目录 | 保留建议 |
|---|---|---|
| 基础输入 | 单行、多行、数字、金额、电话、身份证 | 输入、默认值、必填、占位与校验；不必为售后收集身份证 |
| 时间 | 日期、日期时间、日期区间、时长 | 派驻、请假、补卡、暂离、加班共用，明确时区和单位 |
| 选择 | 单选、下拉、多选、级联、省市区 | 选项版本、关联变化及历史标签快照 |
| 组织人员 | 成员、部门、公司、外部联系人、行业部门 | 保留通用选择能力，明确来自何种主数据及可见范围 |
| 证据 | 图片、附件、手写签名 | 私有文件、预览、下载授权、删除与历史引用约束 |
| 组合与展示 | 明细、说明文字、分栏、评分、公式 | 明细行校验与合计；公式需后端安全计算，不能信任客户端数值 |
| 业务关联 | 地点、客户、工程项目、关联合同、关联申请、预算、发票、收款账户 | 先保留目录；与真实业务对象打通需独立开发和权限核对 |
| 禁用能力 | AI、通用 OCR、身份证 OCR、流水号 | 原目录明确禁用；作为扩展候选，不列为已可运行 |

原后端主要验证必填、数字/日期/选项/附件结构等。`display_condition`、`validation_rule`、只读字段、字段编辑权限等配置存在不代表全部在后端强制执行；公式类型目前按数字输入校验，不能当作已有可信服务端公式引擎。

### 5.3 流程节点与人员解析（已有）

来源 S18—S21、S47。

- 节点：审批、办理、抄送、自动节点、条件分支、并行分支；发起人/结束节点用于完整流程表达。
- 处理人来源：指定成员、直属上级、部门负责人、多级主管、申请人本人、申请人选人、表单成员字段、表单部门负责人、角色。
- 指定审批人数上限等校验存在；主管级数配置为 1—8；申请人自选可限定公司、指定成员、指定角色。
- 或签：一人通过节点即可推进；会签：所有待处理人通过；顺签：按顺序产生处理任务；票决：达到通过票数才推进，剩余票无法达到门槛时拒绝。
- 条件：支持等于/不等、包含、空值、数值比较、区间等，条件组组合及优先级命中；每组条件分支要求恰好一个默认分支，选中路径执行后回主干。
- 并行：至少两支，支内要有可执行节点，全部完成后汇聚；明确禁止嵌套并行。非票决节点拒绝和票决不通过应按引擎规则结束，不能概括成“任何人点拒绝都立即结束”。
- 处理人为空有自动通过、自动拒绝、转管理员或转指定人等策略。新系统关键现场例外申请建议默认转指定负责人，空人不能悄悄通过。

“项目负责人”必须从派驻任务/项目数据解析，不能复用原注释里的示例枚举就认定已完整支持。

### 5.4 实例、任务、动作与异常（已有/部分）

来源 S20—S26。

- 核心实例状态：待审批、已通过、已拒绝、已撤回；任务保存处理人及节点/并行支信息，动作保存意见和时间。
- 普通处理动作实际支持 `approve/reject/transfer`；转审需接收人；非当前待办人不得审批。
- 申请人只可撤回 pending 实例；不能据配置字段就宣称已通过后可撤销、任意退回重提、加签减签全部完成。
- 委托代理、批量审批、催办、已办/待办/我的申请/抄送都有服务与接口。
- 模板管理人、发起范围、实例查看权限有实现；需要用新项目/现场权限替换单纯部门范围。
- 重复审批人策略和超时小时数字段已保存/快照化；本次未找到对应完整定时执行与去重闭环，列为部分能力。
- 意见必填有部分执行逻辑；不能把签名控件等同于审批动作的签名强制、电子签约或法律认证。

### 5.5 审批结果回写（已有，但后台处理能力需补齐）

来源 S11—S13、S20、S48。

1. 审批终态写业务事件；事件包含实例、业务对象及绑定信息。
2. 本地消费者接收，按事件/消费者记录成功、跳过、失败和次数。
3. 考勤消费者建立或更新影响行；补卡另外产生 `source=approval` 的流水并重算日结果。
4. 撤销类事件会撤销有效影响；对已经落入基础记录的副作用必须验证能否完整冲正。
5. 月汇总刷新避开锁定快照；日重算服务目前主要是 dirty 标记，没有看到完整自动物化工作器。
6. 事件失败有退避和重新分发入口；存在接口不等于已部署自动补偿调度。

新系统页面应分别显示“审批已通过”和“业务已生效/生效失败待重试”。业务重算必须幂等，并能从原始事件、有效审批影响和固定规则版本重建结果。

## 6. 手机端与管理端应如何保留

### 6.1 现场人员手机端

保留原登录、工作台、打卡、规则说明、个人日历/月统计、动态申请、我的申请、审批详情、消息、附件预览和个人信息。新增任务与现场选择、今日派驻、到场/离场/暂离/返场、核验任务、最近证据时间、异常申诉与交接记录。

手机首页最重要的信息：今天去哪、几点开始、当前现场、当前判断及更新时间、下一次要完成的动作。无定位权限、证据过期、上传失败、没有派驻、规则缺失均给具体原因；不能统一提示“打卡成功”。

### 6.2 负责人手机端

保留团队考勤、审批中心和人员查询，新增按授权项目的应到/已核验/暂离/已离场/待核验列表、超时异常、派驻变更、替班和人工复核。负责人可兼现场人员，两种视角共用身份。

原 `TeamAttendancePage` 只拉取首批 30 人再逐人请求月汇总；其今日卡片使用的 `late_count/absent_count/total_scheduled/clocked_in` 与原服务返回 `late/absent/total/checked_in` 不一致。不能直接搬为售后监控首页，必须改为有权限范围的聚合接口。

### 6.3 PC 管理端

建议菜单：现场总览、客户与项目、现场设置、陪产任务、派驻与排班、打卡及核验证据、异常工单、考勤规则、审批中心、模板管理、日/月报与确认、人员组织、角色权限、通知与事件监控、系统设置。

原考勤页和审批页可复用交互及业务规则；提炼时按模块拆分大页面，避免新系统继续把流程、字段、权限和统计全部写在一个页面中。

## 7. 售后现场状态与业务流程（新增建议）

### 7.1 把三类状态分开

| 维度 | 建议状态 | 说明 |
|---|---|---|
| 任务/派驻 | 草稿、待审批、已安排、执行中、暂停、完成、取消 | 描述工作安排，不证明在场 |
| 当前现场判断 | 未到场、最近核验在场、批准暂离、已离场、超时未核验、定位待核验、不在服务窗口 | 必须带最近证据时间和判断原因 |
| 日结果/异常 | 正常、迟到、早退、缺证据、工时不足、越界、已解释、待复核、争议中 | 可同时多标签，不用一个枚举覆盖全部事实 |

“最近核验在场”条件建议为：有效派驻 + 当前服务窗口 + 最近有效到场/返场/复核证据仍在有效期内 + 无后续离场事件。有效期是业务参数，不是 GPS 自动保证。

定位精度不足、时间戳过旧、断网没有上传、新证据与已有证据冲突时置待核验；未复核表示缺少证据，不自动断言人员已经离开。

### 7.2 正常闭环

```mermaid
flowchart LR
    A[维护客户项目现场] --> B[创建陪产任务及规则]
    B --> C[派驻审批与排班]
    C --> D[人员手机到场核验]
    D --> E{证据有效}
    E -->|是| F[最近核验在场并显示时间]
    E -->|否| G[待核验及异常工单]
    F --> H[期间复核或暂离返场]
    H --> I[离场及服务记录]
    I --> J[日结果及主管确认]
    J --> K[月报确认锁定]
    G --> L[补充证据或异常审批]
    L --> J
```

### 7.3 应到、暂离与复核

1. 应到清单来自已发布的派驻/班次，未打卡的人也必须在清单中。
2. 到场超宽限未有有效证据，形成异常待办并提醒本人及负责人；需要配置升级时限和通知去重。
3. 临时离场申请批准后可进入批准暂离；应保存实际离开和返场证据，批准时间不等同实际时间。
4. 定时复核、负责人临时复核和可选随机核验均生成可审计任务；错过窗口形成“未响应”，而非自动判旷工。
5. 新有效证据会更新最近核验时间；过期后自动转为超时未核验；必须有后台定时任务，不能依赖用户打开页面触发。
6. 离场后若需返场，应产生新的现场会话/区间；一次全天最早最晚卡不够表达。
7. 夜班归班按现场时区和班次实例 ID，禁止仅用服务器 `date.today()`。

### 7.4 异常与人工认可

异常处理链：发现 → 指派负责人 → 员工说明/补充附件 → 审批/复核 → 生效 → 关闭；拒绝则保留异常并通知。调整必须记录操作者、理由、旧值、新值、依据和版本。

人工认可应写“认可该时段服务”或“异常已解释”，不能补造 GPS 点。批准结果、位置证据和结算认可必须能分别查询。

## 8. 宽范围模板库（新增配置建议）

以下是建议预置模板，不表示原仓库已有这些售后模板。阈值与审批角色暂用可配置参数，不在代码中写死。

| 模板 | 关键字段 | 默认流程建议 | 通过后的业务效果 |
|---|---|---|---|
| 派驻/陪产安排 | 客户、项目、现场、人员、起止、班次、服务内容 | 发起人 → 项目负责人 → 售后负责人 | 建立派驻及排班；不生成到场证据 |
| 派驻延期/提前结束 | 原任务、调整日期、理由、接替安排 | 项目负责人 → 售后负责人 | 生成新安排版本，保留旧版 |
| 替班/交接 | 原人员、接班人、交接时间、事项、附件 | 现场负责人 → 接班人办理 | 调整派驻，交接签收 |
| 跨现场调配 | 原现场、新现场、移动时间、理由 | 两现场负责人并行 → 售后负责人 | 验证时段冲突后调整安排 |
| 补卡 | 目标班次、卡点、申报时间、原因、证据 | 现场负责人 → 售后管理 | 新增审批来源修正，不伪造原始采集 |
| 定位异常/范围外到场 | 现场、当前定位、精度、照片、说明 | 现场负责人 → 例外复核人 | 认可或拒绝本次例外，保留风险标签 |
| 临时离场/外出 | 开始、预计返回、原因、交接人 | 现场负责人 | 生成允许暂离时段 |
| 请假 | 假种、起止、时长、附件 | 现场负责人 → 售后负责人（按时长分支） | 更新应到义务及考勤影响 |
| 出差/行程 | 项目、行程、起止、目的、预计费用 | 项目负责人 → 售后负责人 | 更新行程，不自动显示现场在场 |
| 加班/延时陪产 | 班次、起止、原因、结算方式 | 现场负责人 → 售后负责人 | 生成认可时段；与有效证据求交或按规则结算 |
| 未复核申诉 | 核验任务、错过原因、补充证据 | 核验负责人 → 售后管理 | 关闭或保留异常，不改原任务事实 |
| 陪产日报 | 项目、班次、工作、设备问题、未完成项、附件 | 员工 → 现场负责人办理/确认 | 归档日服务记录 |
| 客户现场确认（可选） | 日期、人员、服务内容、问题、确认身份 | 内部审核 → 客户确认 | 独立确认记录，不默认客户有全部内网权限 |
| 月度服务确认 | 期间、项目、出勤、认可时长、争议 | 人员确认 → 项目负责人 → 售后管理 | 形成锁定快照 |
| 锁定后调整 | 原快照、差异、理由、证据、影响期间 | 项目负责人 → 售后管理 | 生成调整版本并重新确认 |
| 现场围栏/规则变更 | 旧值、新值、原因、生效日期、影响范围 | 现场负责人 → 售后管理 | 发布未来规则版本；历史按原版计算 |
| 外协人员准入（可选） | 单位、人员稳定标识、服务范围、有效期 | 售后管理 → 项目负责人 | 开通限定项目权限及到期停用 |
| 服务费用/补贴（可选） | 任务、天数、金额、票据、计算依据 | 负责人 → 财务 | 输出结算数据；不直接支付 |

## 10. 保留与删减原则

优先保留规则、班次、日历、流水、申请资格、动态模板、流程、附件、日志、通知、回写和报表。这些存在依赖关系，不能只删除菜单就认为安全拆除。

业务上可先关闭：调休余额、薪资费率、补贴费用、客户外部确认、随机核验、原生 App、复杂票决、多级主管、委托、打印增强。关闭后仍须保留历史数据读取能力；不允许停用一个模板就让已产生的实例或附件无法打开。

完整 HR 招聘、绩效、人才、培训、工资发放、行政资产、聊天会议与本系统主闭环无直接关系；清单中保留“外围备选”用于后续取舍，不纳入第一期强依赖。

## 11. 暂定假设与待业务选择参数

本方案暂按内部售后人员为主、可扩展外协、手机 H5 优先、国内现场默认 Asia/Shanghai、独立系统且预留平台接入接口设计。未假设已开通企业微信、已拥有客户账号或已接入门禁。

需要后续选择的参数：到场宽限、围栏半径、精度门槛、证据有效期、定时复核频率、暂离上限、照片保留期、补卡窗口/月次数、锁月日期、最低服务分钟、异常升级时限、客户是否参与确认。

这些均进入管理配置和规则版本。本文没有把示例阈值当作现行公司制度，也不从原 HR 的加班费率推断售后结算政策。
