源码位置：`Jaydon-Lidong/aftersales-field-management` 仓库根目录，以及 `shangzeng20020703/Shang/Tegene/售后管理系统`。当前售后功能及后续修改均在本项目维护，原 EHR 仅作为源码来源，不向 EHR 仓库提交或部署改动。

基于 EHR 固定提交 `051b38f04b0e33f1e624da35fa57ecae9fd4974f` 提取的独立基础版，包含后端、电脑管理端、手机网页端和本地演示环境。

**UI/UX 沿用原 EHR。** 手机首页、工作台、底栏、个人中心和管理端框架已恢复原版；打卡、考勤规则、审批及模板继续使用原组件，详见 [界面沿用核对](docs/08-原版UIUX沿用与核对.md)。

## 功能

### 考勤看板

「考勤总览」提供人员规模、打卡进度环形图、异常类型柱状图、项目人员对比和近 7 天柱状图；支持日期、项目筛选及明细搜索、异常筛选、分页和 CSV 导出。数据来自本系统花名册、项目参与区间和考勤结果，接口为 `GET /api/v1/field/dashboard`。

- 当前在职人数：花名册中在职 / 试用人员，包含停用但未离职账号；不随日期回溯。选择项目时仅统计当前参与该项目的在职人员；负责人仅可看可见项目的人员。
- 当日项目人数：所选日期参与项目的人员去重；同一天 A → B → A 只算一人。历史离职人员仍保留在当日记录中。此数是参与人数，不是按工作日历计算的应出勤人数。
- 打卡进度：任一项目有上班或下班卡即计入已打卡；当天所有项目记录均有上下班卡才计为已齐卡，其余为打卡未齐或未打卡。已齐卡不等于无异常。
- 异常人数：按人员去重；类型包含迟到、早退、缺卡、定位 / WiFi、待核对、旷工和其他异常，一人可有多类。只读取已生成的异常，不把未打卡直接认定为旷工，也不在查看看板时重算历史。
- 项目对比：各项目内部去重，展示参与人数最多的 6 个项目；跨项目人员会在各项目出现，因此项目人数之和可能大于总人数。近 7 天以所选日期为末日，按北京时间工作日统计。

`scripts/test_field_dashboard.py` 使用隔离数据库验证去重、项目筛选、权限、离职历史、空数据及跨项目规则分段统计。

### 规则配置与使用

1. 管理员进入「考勤管理 → 考勤规则」，新增规则并配置时间、定位 / WiFi、照片要求，保存并启用。新增或复制的规则按项目使用，不自动套用到全部员工。
2. 在「项目库 → 配置项目」选择这条规则，再从花名册选择或导入人员。项目中只保存规则关联，不重复维护规则内容。
3. 工程师从员工端进入打卡，系统按本人当前项目自动匹配项目规则。项目负责人可选择规则、添加 / 调动 / 移出人员；共用规则仅管理员和 HR 可维护。

一个人同一时刻仅属于一个项目。调动即时结束原参与区间并开启目标项目区间，手机无须重新登录；提交时服务端复核项目和规则版本。新打卡按所在项目规则生成考勤分段，各段保存规则快照、原始流水 ID 和计算结果，再汇总到每日记录。A → B → A 会形成三段；缺少下班卡的旧段标记待核对，不自动补卡或跨项目配对。规则修改只影响新分段；已打卡的段保留原规则。

项目抽屉支持 Excel / CSV 导入已有花名册人员，导入前预览核对；遇到非在职、姓名手机号不匹配、重复或已有项目的人员时整批不写入。花名册重复导入保留原密码和角色。人员状态改为离职会关闭当前和未来参与区间；恢复在职后须显式启用并重新分配项目。

数据库版本 4 为新增参与区间和考勤分段表；原按日期安排的记录会幂等补充区间，不删除历史班次和考勤。执行 `python -m app.bootstrap` 后再启动。验收脚本 `scripts/test_project_membership.py` 使用隔离临时数据库覆盖 A/B/A 调动、规则快照、离职会话锁定和历史保留。

数据库版本 5 新增售后名册补充资料表。下载的 Excel 保持《售后名册》的 18 列原名和原顺序，末尾追加公司在职状态，仅包含表头和一行虚构示例。人员页面使用紧凑分页列表，全部资料在编辑侧栏分组维护。手工填写姓名和联系电话后保存，自动开通手机号账号，默认密码 585858。系统已安排人员的当前项目取实时参与记录；名册中的项目、组长和部门文字不自动建立项目安排、主管权限或组织关联。是否进入企微、年龄、入职天数按登记值维护。

数据库版本 6 将旧的待入职、停用标签归为在职，保留原账号启停状态；试用期统一存储为试用。名册只接受在职、试用期、离职三种状态，在编辑中修改，列表仅展示。离职自动锁定登录、结束当前项目参与并保留历史考勤及审批数据。

后台已移除假期管理和公司管理页面、菜单及路由，已有请假审批与历史数据保留。普通售后工程师只使用员工端；后台登录及每次页面导航均由服务端复核管理权限，手机端登录状态不能直接进入后台。

## 安装与启动

需要 Python 3.11+、Node.js 22+、npm；有 `uv` 时安装脚本优先使用 `uv`。

```sh
./scripts/setup.sh --admin
python3 scripts/dev.py start
python3 scripts/dev.py status
python3 scripts/dev.py stop
```

安装脚本创建本项目虚拟环境、安装依赖、非破坏性初始化本地 SQLite 空表；全新环境用 `app.bootstrap --admin` 初始化管理员与模板，只有显式运行 `./scripts/setup.sh --demo` 才创建演示数据。已有数据不会被清空，已有账号密码不会被重置。启动脚本仅管理本项目启动的进程；端口被其他进程占用时会报错。

- 本地数据库：`backend/data/aftersales.db`
- 上传文件：`backend/uploads/`
- 本地会话密钥：`backend/data/.session-key`
- 运行日志：`.runtime/`

## 接入 Tegene 项目库

**2026-09-30 已接通正式项目。** 本地管理端实际读取 `i.tegene.com` 的 89 个项目，数量与正式库核对一致。使用独立机器应用 `Aftersales Project Reader`，凭据仅保存在 `backend/.env`；人员、售后负责人和排班仍保存在本系统。

接入复用 Tegene 现有项目接口和只读集成角色 `pms-device-integration`。Logto 为售后应用单独签发 token，现有机器 token 映射中仅增加此应用的项目读取分支；其他应用映射保持原样。未修改 Tegene 业务代码、项目资料或业务数据库，也没有重启正式服务。实际 `/api/me/permissions` 仅返回 `pms:project:read`；无效凭据返回 401，访问 Logto 管理 API 返回 403。

使用路径：管理端“项目库”搜索或筛选项目，打开“配置项目”。管理员先指定本系统负责人，负责人选择打卡规则、添加参与人员和起止日期。手机端“我的项目”查看自己的参与日期，再进入打卡页；系统自动带出当天项目和规则。

### 精简后的业务逻辑

1. **项目库**：Tegene 是项目编号和名称的来源，售后系统不重复维护客户、现场或另一份项目列表。
2. **项目配置**：每个项目一个负责人、一套当前打卡规则。管理员指定负责人，负责人在自己项目内选择已有规则并分配可管理人员；规则模板由管理员在“考勤管理”维护。
3. **人员参与**：人员必须有起止日期，所选日期每天生成项目班次；同一人同一天不能同时属于两个项目或重复排班。批量添加中任一人失败，整批不保存。
4. **员工打卡**：按照人员和日期匹配项目班次，自动读取打卡时段、定位/Wi-Fi/照片等规则，员工不选择项目、现场或规则。尚未分配项目时显示当前个人考勤规则，不冒充项目考勤。
   自由工时规则选择具体小时数时，双卡齐全但实际工时不足会在考勤记录和报表中标为异常，并注明差额原因；选择“不限制”不做最低工时校验。
5. **考勤查看**：“考勤总览”按项目查看应到、打卡与异常；更换项目规则更新明天起的未记录班次，今天及历史班次保持原规则。后续已有考勤或月份锁定时拒绝修改。

不再提供独立的客户、现场、派驻列表。旧数据关联与历史记录保留，避免破坏已有考勤。本轮未改动既有正式项目的负责人或参与人员。

来源确定为 `https://i.tegene.com/api`，调用现有 `GET /pms/projects`，仅读取当前凭据有权查看的项目。读取全部项目需要上游授权全项目数据范围；不会绕过上游权限。完整项目库由售后管理员读取并指定负责人；负责人管理自己项目的规则和参与人员。

在 `backend/.env` 配置（不得放到前端或提交密钥）：

```dotenv
TEGENE_API_BASE_URL=https://i.tegene.com/api
TEGENE_TOKEN_URL=https://iam.tgjqr.com/oidc/token
TEGENE_CLIENT_ID=<专用服务账号 ID>
TEGENE_CLIENT_SECRET=<专用服务账号密钥>
TEGENE_RESOURCE=https://api.robot-erp.local
TEGENE_SCOPE=pms:project:read
```

上游账号需要 `pms:project:read` 权限及覆盖全部目标项目的数据范围。短期联调也可只配置 `TEGENE_ACCESS_TOKEN`，到期后须更新；长期接入使用服务账号。配置后重启本地服务。

接入关联使用“来源地址 + Tegene UUID”，不靠名称或同号自动合并。编号和名称由 Tegene 维护；刷新项目库展示最新资料，管理员保存该项目配置时同步本地关联资料。项目负责人与考勤规则由本系统配置，历史班次保留。项目重名或同号冲突会提示核对。源接口不可用时显示错误，已接入项目和本地历史排班仍可使用。

结构升级只追加关联表，运行 `PYTHONPATH=backend backend/.venv/bin/python -m app.bootstrap` 后重启。验证命令：`backend/.venv/bin/python scripts/test_tegene_projects.py`，使用临时数据库和模拟上游，不触碰正式项目。本次实现按仓库主干 `7ec6e0bd1785d4a7f754fd7e4c0b02f5700ca5cf` 的 API 契约验证；未配置真实凭据前不代表正式数据已接通。

## 配置定位服务

复制 `backend/.env.example` 为 `backend/.env`，配置后重启后端：

- `TENCENT_MAP_WEB_SERVICE_KEY`：后端坐标转换、逆地址解析和地图代理。
- `TENCENT_MAP_BROWSER_KEY`：浏览器地图展示 Key 的服务器回退值。管理员专用后端接口 `GET/PUT/DELETE /api/v1/system-settings/tencent-map` 可管理数据库覆盖值；后台保存值优先，清除后回退到此环境变量。修改数据库覆盖值后刷新已打开的手机端地图页即可生效。管理端不提供配置页面。浏览器 Key 应在腾讯控制台限制实际使用域名；服务端 Key 不下发给浏览器。

演示规则不要求 GPS，便于先体验流程。正式现场需在考勤规则中配置真实坐标、范围和照片要求。GPS 规则采用腾讯地图坐标口径；IP 地址定位只作地址提示，不作为打卡坐标。
