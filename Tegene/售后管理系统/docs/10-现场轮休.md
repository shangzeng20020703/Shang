# 现场轮休

适用于陪产日期由现场安排、默认上六休一的项目。固定时间上下班、自由上下班及原排班模式继续保留。

## 使用顺序

1. 管理员在考勤规则中选择「现场轮休」，设置每日要求工时、考勤日开始时间、地点和照片要求。本模式不勾选星期，不允许选择工时不限制。
2. 在项目库将规则分配给项目，并添加参与人员。项目负责人打开「现场轮休」，选择人员、发布日期范围及周期起点。周期起点是第一天上班，第七天轮休，与星期无关。
3. 预览后可修改指定日期的安排，再发布。发布时校验预览版本；其他人修改或规则变化后须重新预览。周期发布只能从今天及规则生效日起，已有打卡不能被周期生成覆盖。
4. 临时变更可批量调整已发布日期，也可由员工从手机打卡页进入「排班与待休」申请，负责人审批。未发布日期可提交调班申请，负责人明确确认后才建立当日安排；不会按打卡自动推定正常。
5. 在原定轮休日陪产，正常打上下班卡。员工申请事后出勤确认，或负责人从排班表发起核对；完整打卡是确认前提。达到规则工时建议一天，达到一半建议半天，不足一半由负责人说明原因后确认零或半天，最多一天。
6. 手机端可查看个人月历、申请调班或使用待休。调休只在原上班日使用，正常轮休不扣余额。半天调休将当天要求工时减半，不限制上午或下午时刻。

## 日期和余额口径

- 周期连续计算。例如连续陪产14天，原定第7天及第14天均为轮休；两天均满足工时并确认后，可得两天待休。
- 临时调班、正常轮休和已批准调休不自动重置后续周期。负责人可从未来日期重新生成周期，旧日历和调整日志保留。
- 公司节假日分类仍保留；现场是否需要上班按个人已发布日历判断。出勤产生的加班费仍沿用既有策略。
- 原定轮休日的自动加班转调休停用，由轮休确认流水入账；已有显式加班转调休来源会拦截轮休确认。反向重复转换也会拦截并进入既有事件失败诊断，需核对来源后处理。
- 待休以半天为最小单位，独立于旧假期余额记录，跨项目保留，不自动清零或过期。支出审批时扣减，撤销时退回，不可透支。两次并发审批也不能透支同一账户。
- 同一原定轮休日不能重复申请已批准或待审的出勤确认。批准后再更新下班卡或补卡，确认记录提示「打卡已变化，需复核」，原入账金额保留；须有原因地撤销后重新确认。已用额度导致余额不足时不能直接撤销来源。
- 员工不能修改排班或余额。负责人只能管理负责项目，管理员、HR可跨项目管理；员工仅查看本人。原定安排、规则快照、原因、操作人及账户流水保留。
- 显式调整会重算涉及日期，通过现有重算任务完成；不因新增规则自动重算历史。已锁定月份拒绝调整，须先按既有流程解锁。

## 接口与结构

新增 `/api/v1/rotation`：`GET /calendar`，`POST /projects/{id}/preview`、`/publish`、`/adjust`，`POST /claims` 和 `/claims/{id}/review`。日历限366天，单次申请限62天，出勤确认逐日提交。发布要求预览返回的 revision；日期调整支持逐人日期版本检查。

新增四张独立表：`field_rotation_days`、`field_rotation_claims`、`field_rotation_accounts`、`field_rotation_ledger`。schema版本9只新增表，不改旧表列、不迁移旧调休余额。升级前备份，执行 `python -m app.bootstrap`；不能仅重启API跳过结构初始化。

回退前保留完整数据库备份及新增四表。版本8代码不能处理本模式；已有轮休项目时不可直接用旧代码继续打卡。应先停止轮休业务写入，在隔离副本核对恢复点及此后新增记录，再制定切换步骤。源码版本副本不包含业务数据库。
